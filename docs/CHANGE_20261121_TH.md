# การเปลี่ยนแปลง 21 พ.ย. 2026: เพดาน BUY ต่อวันนับแบบ net (BUY − SELL ที่ fill แล้ว)

## ทำไม

PROD RGTI วันที่ 20 พ.ย. 2026 (`webull_lego_order_dispatch_locks/RGTI_34ef426fd4e78627899ea1ef`):

| run_id | ฝั่ง | ผล |
|---|---|---|
| `2fd69c04bd3b72da95bc11e1cfd589c8` | BUY 10.63 | FILLED |
| `bc2939892d957461548e3fc945311b27` | SELL 6.55 | FILLED |
| `ba4d8146b1643a631781640fa33a0637` | BUY 7.06 | FILLED |
| `bad1bbfa5d556f967026eb86f3828fec` | BUY 6.83 | FILLED |

counter `{count: 4, buy_count: 3}` ⇒ BUY ถัดไปถูกปฏิเสธ `session BUY limit reached (3 BUY orders per session)`
ทั้งที่ซื้อสุทธิแค่ **+2** (USAR วันเดียวกันก็ `4 / 3`). เจ้าของบัญชีให้เปลี่ยนจากนับ BUY **รวม** เป็นนับ **net**

## กติกาใหม่ (ตามการตัดสินใจของเจ้าของบัญชี)

| เรื่อง | ก่อน | หลัง |
|---|---|---|
| สิ่งที่ `LEGO_MAX_SESSION_BUY_ORDERS` จำกัด | จำนวน BUY รวมต่อวัน | **net BUY** = BUY ที่จอง − SELL ที่ **fill แล้ว** ต่อวัน |
| BUY ผ่านเมื่อ | `buy_count < N` | `buy_count − sell_count < N` |
| BUY นับตอนไหน | จองก่อน Place, ไม่คืน | เหมือนเดิม |
| SELL | ไม่คืนโควตา BUY | SELL ที่ broker รายงาน fill (จำนวน fill > 0) ปลด BUY 1 ครั้ง |
| SELL ถูกเพดาน BUY บล็อกไหม | ไม่ | ไม่ (เหมือนเดิม) ใช้แค่เพดานรวม `LEGO_MAX_SESSION_ORDERS` |
| net ติดลบ | – | ได้: SELL, SELL แล้ว BUY ได้ถึง 5 ครั้ง (net +3) |

ตัวอย่างข้างบนหลังเปลี่ยน: BUY, SELL, BUY, BUY ⇒ net +2 ⇒ BUY ครั้งที่ 4 ผ่าน (net +3) ⇒ BUY ถัดไปจึงรอวันถัดไป

ไม่เปลี่ยน: ชื่อและค่า env (`LEGO_MAX_SESSION_BUY_ORDERS=3`), `policy_hash`, เพดานรวม, status
`SESSION_BUY_CAP_REACHED` (WARNING ไม่ปลุกคน) และการหยุดก่อน Preview

## ทำงานอย่างไร

- `execution_session` ใน dispatch lock มี field ใหม่ `sell_count` (SELL ที่ fill แล้ว) คู่กับ `buy_count` (BUY ที่จอง)
- `broker_circuit.record_outcome` บันทึก credit ของ SELL ที่ fill ใน transaction เดียวกับใบรับผล broker
  ⇒ ไม่เพิ่ม RTDB round-trip และนับครั้งเดียวต่อ run (`last_outcome_run_id`, `last_sell_credit_run_id`)
- credit ได้เฉพาะ run ที่จองล่าสุดใน counter นั้น (`last_run_id`) และไม่เกินจำนวน SELL ที่จองไว้ (`count − buy_count`)
- BUY ถัดไปแซง SELL ที่ยังไม่รู้ผลไม่ได้: ระหว่างนั้น fence ยังถือ run ของ SELL (decision เป็น `PASS_RECOVERY_BLOCKED`)
- ข้อความใหม่: `session net BUY limit reached (net 3 = 4 BUY - 1 filled SELL; max 3 net BUY per session)`
- `python ops.py status` แสดง `execution_session` พร้อม `net_buy_count`

## ข้อจำกัดที่ตั้งใจไว้ (เข้มกว่า ไม่หลวมกว่า)

- SELL ที่ fill บางส่วนแล้ว cancel นับเป็น 1 (นับเป็นออร์เดอร์ ไม่ใช่จำนวนหุ้น เหมือนฝั่ง BUY)
- BUY ที่จองแล้วส่งไม่สำเร็จยังนับ
- SELL ที่ปิดด้วย fill anomaly / admin reconcile / manual (ไม่ผ่าน `record_outcome`) ไม่ปลดโควตา BUY
- counter ก่อนมี `buy_count` (ถือว่าทุกครั้งเป็น BUY) หรือที่ผ่าน `migrate_market_day` ไม่มี SELL ให้ credit

## ความเข้ากันได้และการ deploy

- dispatch lock ยัง **schema 5**: revision เก่าไม่รู้จัก `sell_count` ⇒ นับ BUY รวมแบบเดิม = เข้มกว่า (rollback ไม่หลวม)
  และ `{**session}` ของมันเก็บ `sell_count` ไว้
- ไม่ต้องแก้ข้อมูล RTDB: counter เดิมไม่มี `sell_count` = 0; วันตลาดใหม่เริ่ม counter ใหม่เอง
- โค้ดเปลี่ยน ⇒ candidate hash เปลี่ยน ⇒ ต้อง plan และ deploy PROD ใหม่ตามขั้นตอนปกตินอกเวลาตลาด
  (`deploy/cloudshell-prod-live.sh`); ค่า env เดิมทุกตัว
