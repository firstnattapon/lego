## ข้อค้นพบและการแก้ไข

1. **Auth retry storm:** การสร้าง client ใหม่ล้มเหลวด้วย 401 สอดคล้องกับการ refresh cache แต่หลักฐานยังแยกไม่ได้ว่า key ถูกเปลี่ยน, สิทธิ์ถูกถอน หรือปัญหา gateway ห้ามสรุปว่า token หมดอายุแน่นอน เพิ่ม circuit breaker ใน RTDB แยก account/environment ใช้ cooldown 60/120/240/480/960/1800 วินาทีและ capped ต่อไป เปิด probe ทีละเจ้าของด้วย transaction และ lease 45 วินาที จึงคงอยู่ข้าม cold start; key rotation ไม่ล้าง cooldown ของบัญชีเดิมโดยอ้อม
2. **การฟื้นตัว:** ตรวจทั้งก่อน tick, ก่อนใช้ cached client และก่อน HTTP SDK request เมื่อ trading request สำเร็จจาก probe ที่เป็นเจ้าของจึง resolve warning การพักตอบ HTTP 200 พร้อม business_status=AUTH_BACKOFF และ retry_after เพื่อไม่ให้ Scheduler retry เพิ่ม ต้อง monitor business_status ด้วย ไม่ใช่ดู HTTP 2xx อย่างเดียว ออเดอร์ที่ส่งแล้วเก็บ fence/สถานะเดิมและไม่เสีย reconcile budget ระหว่าง auth outage
3. **Broker reject:** อ่าน containers ซ้อนได้ แต่ปฏิเสธหลาย orders/siblings หรือ identity ขัดกัน ไม่เลือก fill ของรายการแรกโดยเดา เก็บ reason จาก nested detail/place response พร้อม redaction และ terminal_reason ถ้า broker ไม่ให้เหตุผลจะระบุชัดว่าไม่ทราบ ไม่มีการสร้างเหตุผลย้อนหลังให้สองออเดอร์เก่า
4. **Timeout:** connect/read ceiling เป็น 5/10 วินาทีภายในเวลาที่เหลือของ tick ไม่อ้างว่าแก้ network outage ได้ทั้งหมด และยังไม่ retry Place อัตโนมัติ
5. **Token storage:** Secret Manager ต้องใช้ resource เต็ม `projects/PROJECT/secrets/NAME` ไม่ใช่ชื่อสั้น แหล่ง token ที่ hydrate สำเร็จและตรงกับ local cache จึงผ่าน durability check; แค่ตั้ง env ไม่เพียงพอ โหลด latest ซ้ำเมื่อสร้าง client ใหม่เพื่อรับ rotation และปฏิเสธ secret หมดอายุก่อนเขียนทับ cache ล้าง client/auth profile ที่สร้างไม่สำเร็จ
6. **Token rotation:** runtime อ่าน secret เท่านั้น การหมุน token ยังเป็นงาน operator ผ่าน 2FA/SDK และ `ops.py bootstrap-auth --apply` ก่อนเข้า refresh margin (ค่าเริ่มต้น 3 วัน) ไม่อ้างว่าตั้ง Secret Manager แล้วจะรันได้ไม่สิ้นสุดโดยไม่ดูแล ต้องมีผู้รับผิดชอบและ alert สำหรับ expiry การหมุน token ต้องทำให้ durable secret และ broker ตรงกัน แล้วตรวจ warm/cold instance
7. **Dashboard:** แสดง ACTIVE/RESOLVED/HISTORY และ retry_after แม้ยังไม่มี committed row; จัด reject_reason/terminal_reason ไว้ด้านหน้าของ order audit ห้ามนับ historical warning ว่าเป็นเหตุขัดข้องใหม่

1. Review และ CI ทั้งสอง PR ผ่าน รวม dependency/secret scan และ Firebase Emulator; เก็บ candidate manifest จาก artifact ที่จะ deploy จริง
2. UAT soak อย่างน้อยหนึ่ง session รวม restart, auth failure/recovery, partial fill/cancel, delayed fee และ unknown Place outcome; ยืนยันไม่มี Place ซ้ำและเงิน/หุ้น/fees กระทบยอดได้

4. Read-only smoke ตรวจ environment, account ownership, positions, buying power, open orders และข้อมูลราคาสดจาก PROD พร้อมตรวจ auth expiry/rotation owner
5. จัด alert AUTH_BACKOFF, TOKEN expiry, fee overdue, unresolved fence, DNA exhaustion และ missed heartbeat พร้อมผู้รับผิดชอบ รายงานนี้ไม่ได้สร้างช่องทางแจ้งเตือนภายนอก

7. ใช้ `ops.py check` ตรวจ candidate_matches และ `ops.py release-binding` เพื่อสร้าง binding ของ account/environment/candidate ที่ทดสอบจริง ก่อนเปลี่ยน trade/active=true โดย operator
8. เมื่อ rollback ให้ observe/active=false, ยังรัน recovery สำหรับคำสั่งที่ส่งแล้ว ห้ามลบ outbox/fence เพื่อแก้ค้างโดยไม่มีหลักฐาน broker
