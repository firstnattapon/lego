### สิ่งที่สรุปได้และสิ่งที่ยังสรุปไม่ได้

`reason not supplied by broker` เป็น fallback ของแอปเมื่อ parser หา textual
reason ไม่เจอ ไม่ได้พิสูจน์ว่า broker ส่งข้อความนี้ และไม่ใช่สาเหตุปฏิเสธคำสั่ง
Place สำเร็จหมายถึงรับคำขอ ไม่ได้หมายถึง fill; ledger เดิมไม่ควรถูกเติม fill สมมติ

เอกสารปัจจุบันระบุว่า quantity ของหุ้นสหรัฐฯ ใช้ทศนิยมได้ และ Order Detail
ระบุ FAILED แต่ไม่รับประกัน textual rejection reason จึง **ไม่ยืนยันข้อสรุปในร่าง
ว่า UAT ไม่รองรับเศษหุ้น**: simulator, สิทธิ์บัญชี, instrument, liquidity หรือ
ข้อจำกัดอื่นยังเป็นสมมติฐาน ต้องตรวจ detail รอบใหม่หรือให้ Webull ตรวจ order ID

## การแก้ไข

1. **ตัดวงจรหลัง broker FAILED/REJECTED 3 ออเดอร์** เก็บ durable state ใน
   account/environment/symbol dispatch fence จึงเปลี่ยน DNA/strategy chain
   แล้วหลบ halt ไม่ได้ นับก่อนเขียน terminal outbox; crash/replay ของ run เดิม
   ไม่นับซ้ำ และ callback ของ run เก่าเปลี่ยน state ของ run ใหม่ไม่ได้
   FAILED ที่มี partial fill ยังนับเป็น reject แต่ต้อง reconcileเงินจริงตามเดิม
   Positive terminal fill ของออเดอร์อื่นรีเซ็ต streak; partial ที่ยังไม่ terminal,
   PASS, timeout, Preview error และ CANCELLED ศูนย์หุ้นไม่รีเซ็ต streak
   เมื่อ halt แล้วต้องให้ operator reset แม้ภายหลังพบ fill

2. **Recovery ยังทำงาน**: halt/observe/pause/ข้อจำกัด token สำหรับคำสั่งใหม่
   ไม่ข้ามการติดตามคำสั่งที่เคย Place, รวมถึง fee และ ledger ที่ยังไม่ครบ
   เพิ่ม `PENDING` ตาม Webull contract ใน reconcile states และทำให้ status
   ที่ไม่รู้จักกลับไป UNKNOWN แทนการค้างใน queue โดยไม่ติดตาม
   ตรวจ client order ID และ symbol ใน post-Place polling เช่นเดียวกับ recovery

3. **Diagnostics ส่วนตัว**: FAILED/REJECTED เก็บ `broker_raw_detail` เป็น JSON
   text ที่ปกปิดฟิลด์อ่อนไหวและจำกัด 16 KiB ใน private outbox/archive เท่านั้น
   จำกัด nesting/จำนวน fields/ความยาวข้อความและระบุ truncation เมื่อเกินขนาด
   public order audit และ HTTP results ไม่ส่ง raw detail
   เก็บ broker order ID, request ID ถ้ามี, reject code และ `broker_reason_missing`
   เพื่อประกอบการติดต่อ broker; ไม่เดาสาเหตุเมื่อไม่พบ reason
   Log business status เป็น `BROKER_ORDER_FAILED` / `BROKER_REJECT_HALT`
   พร้อม ERROR severity แม้ HTTP 200 เพื่อให้ Scheduler รับทราบ tick โดยไม่ retry
   การ Place จาก HTTP status อย่างผิดวิธี

4. **`LEGO_ALLOW_FRACTIONAL`** เป็น deployment policy, default true เพื่อคง
   พฤติกรรมเดิม ไม่เพิ่ม strategy setting ตัวที่เจ็ด เมื่อ false ใช้ lot-size
   จำนวนเต็มและ Decimal ROUND_DOWN ใน engine ก่อน commit ทั้ง row และ intent
   ค่าน้อยกว่า lot เป็น PASS_MIN_ORDER; ไม่ปัด holdings ของบัญชี
   intent เก่าที่เป็นเศษหุ้นจะ NOT_PLACED เมื่อปิด fractional ไม่เปลี่ยน quantity
   ระหว่าง Preview/Place; attempted intent เก่ายัง reconcile ตาม quantity เดิม
   template PROD ตั้ง false ในโหมด observe/inactive

5. **Token**: เพิ่ม warning เมื่อเหลือไม่เกิน 7 วัน และ hard floor 24 ชั่วโมง
   สำหรับคำสั่ง PROD ใหม่ทั้งก่อน Preview และก่อน Place โดยเทียบ expiry จริง
   ไม่ใช้ days_left ที่ปัดเศษ Unknown expiry/status ไม่ NORMAL บล็อกคำสั่งใหม่
   Broker-verified token-check-disabled ยังใช้ signed requests ได้
   ไม่ลดความเข้มงวดของ preflight เดิมที่อาจบล็อกก่อนหมดอายุ 3 วัน
   การแจ้งเตือนประเมินใน market decision tick ไม่ได้สร้าง daily scheduler ใหม่
   การดูแล token ในวันหยุดต้องใช้ monitoring ของ deployment ร่วมด้วย

6. **Webhook แบบ optional**: `ALERT_WEBHOOK_URL` เป็น HTTPS receiver ที่รับ
   JSON `{event, symbol, consecutive_count, expires_at}` ไม่แนบ account ID,
   raw payload, secret, URL หรือ exception ลง log
   เหตุการณ์ BROKER_REJECT_HALT / AUTH_BACKOFF / TOKEN_EXPIRY_WARNING
   ใช้ durable cooldown 24 ชั่วโมงต่อ event/scope; failed delivery retry ได้หลัง
   60 วินาที เมื่อมี tick ที่พบ event อีกครั้ง ไม่ติดตาม redirect
   connect/read timeout 1/2 วินาทีและข้ามเมื่อ tick budget ไม่พอ; ความล้มเหลว
   ไม่เปลี่ยนผล trading pipeline ใช้ synchronous bounded delivery เพราะ Cloud
   Run ไม่รับประกัน background thread หลังตอบ HTTP
   **ไม่ได้อ้างว่า URL Telegram/LINE/Discord ใช้ payload เดียวกันได้**:
   ต้องมี receiver adapter ตาม API ของปลายทาง ไม่มีการส่ง webhook ในงาน audit นี้

## Operator runbook

### เมื่อพบ halt

1. ตรวจ `python ops.py status` และ `broker_reject_circuit.halt_id`
   เก็บ `run_id`, `broker_order_id`, เวลา UTC, environment, request ID
   เปิด private outbox ด้วยสิทธิ์ผู้ดูแลเพื่อดู diagnostic; อย่าแชร์ raw export
2. Pause deployment (`LEGO_ACTIVE=false`) และปล่อย recovery จัดการออเดอร์ค้าง
   ตรวจ holdings/open orders/cashflow กับ broker ถ้า fence ยัง unresolved ห้ามลบ
   อย่าส่ง Place ซ้ำเมื่อผลเดิมไม่แน่นอน
3. แก้สาเหตุและทบทวนก่อน reset ค่า chain ledger/DNA/fills ไม่เปลี่ยนตาม reset

```text
python ops.py reset-reject-halt --halt-id HALT_RUN_ID --reason "reviewed broker outcome and corrected cause"
python ops.py reset-reject-halt --halt-id HALT_RUN_ID --reason "reviewed broker outcome and corrected cause" --apply
```

ค่าเริ่มต้น dry-run; `--apply` เปรียบเทียบ halt ID ซ้ำใน transaction และปฏิเสธ
ถ้ามี active dispatch owner หรือ unresolved order fence คำสั่งต้องใช้ config ของ
บัญชี/environment/symbol ที่ต้องการจริง การ reset ไม่ enable trading ให้เอง
counter เริ่มจากผลใหม่หลังอัปเกรด; ไม่ backfill 14 ผลในอดีตโดยอัตโนมัติ
ดังนั้น deployment ที่เกิด incident ต้องคง inactive จน operator ตรวจประวัติแล้ว

### Token rotation

เตรียม token ที่ผ่าน 2FA ตาม Webull แล้วเก็บ token/expires/NORMAL สามบรรทัด
ในไฟล์ส่วนตัวนอก repository จากนั้นใช้ `ops.py bootstrap-auth --token-file ...
--secret projects/PROJECT/secrets/NAME` ตรวจ dry-run ก่อน `--apply`
การ rotate ต้องใช้ account/environment ที่ตรงกัน ตรวจ warm instance และ cold
start หลังเปลี่ยน Secret Manager version ไม่เผยแพร่ token file หรือ terminal dump

## เกณฑ์ก่อนเงินจริงที่ยังต้องทำบน environment จริง

- UAT แบบ whole-share อย่างน้อยหนึ่ง session: มี BUY และ SELL ที่ fill จริง,
  final holdings ตรง, fee มาครบ, broker cashflow/model finalization ไม่ซ้ำ;
  ทดสอบ restart หลัง timeout, pause แล้ว recovery, reject halt และ reset
- ทดสอบ receiver ของ webhook และ Cloud Logging alert policy จริง รวมถึง token
  ใกล้หมดอายุและวันหยุด ตรวจว่ามีผู้รับการแจ้งเตือนจริง
- PROD observe/inactive: read-only smoke ของบัญชีที่ตั้งใจใช้, cash/buying power,
  positions/open orders, instrument capability, token secret และ IAM
- สร้าง candidate hash จาก artifact ที่ deploy จริงและ release binding ที่ตรง
  account/environment/candidate ห้ามนำ binding ของ UAT หรือ revision เก่ามาใช้
- ค่อย enable canary ที่กำหนด symbol/side/quantity/วงเงินชัดเจน แล้วตรวจ fill/fee/
  holdings ก่อนเพิ่มขนาด ไม่มีขั้นตอนเหล่านี้ถูกทำให้โดย PR นี้

การผ่าน unit tests, emulator และ dependency audit ไม่ใช่การรับประกันผล fill,
ความพร้อม operational ของ cloud deployment หรือผลตอบแทนกลยุทธ์
