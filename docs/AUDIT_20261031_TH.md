## F1 — ต้นเหตุ 429

order tick อ่าน positions **สามครั้ง** ผ่าน `webull_io.fetch_snapshot` → `fetch_holdings`: ตอนตัดสินใจ, ก่อน Preview และหลัง Preview (หลักฐานก่อนถึงจุดเดียวกับ Place)
เวลาเริ่มของแต่ละครั้ง = เวลา log − `duration_ms` ของ `lego_operation`; 17 tick ที่อ่านครบสามครั้ง (วินาทีหลังครั้งแรก):

| ครั้งที่สามเริ่มที่ | ผล | tick |
|---|---|---|
| 2.967 · 3.188 · 3.478 | **429** | 18:45 · 14:00 · 16:00 |
| 3.499 | ผ่าน | 17:45 |
| 3.513 | **429** | 17:00 (tick นี้อ่าน balance ด้วย) |
| 3.576 – 5.582 | ผ่านทั้ง 12 | ที่เหลือ |

- ครั้งที่หนึ่งและสองผ่านทุกครั้ง; ขอบอยู่ราว 3.5 s (3.499 ผ่าน / 3.513 ไม่ผ่าน = เวลาใน log คลาดได้ ~15 ms)
- เอกสารบอก 10/30s แต่ gateway บังคับในช่วงสั้น ≈ **2 ครั้งต่อ 3.5 s ต่อ endpoint** (balance / accounts ที่อยู่ในช่วงเดียวกันไม่ทำให้ tick อื่นล้ม)
- ครั้งที่ถูกปฏิเสธไม่ถูกนับ: retry ทั้ง 4 ครั้ง (เริ่ม 3.26–3.68 s หลังครั้งที่สอง) ผ่านหมด
- ต้นทุนวันนี้: 429 + back-off ~2.15 s ที่จุดตรวจสุดท้ายก่อน paper fill; ถ้าล้มติดกันจน retry หมด intent ถูกเลื่อน และเสีย slot ได้เมื่อเกิน decision age 120 s;
  ถ้าวันหนึ่งเป็น trade จะมีการอ่านครั้งที่สี่หลัง Place (`execution_service._finalize_model_ledger`) ซึ่งชิดกว่าเดิม

## การแก้ (ไม่ลดการอ่าน ไม่แตะสูตร / ledger / paper / fence / gate)

- `webull_io._pace` (GCRA บน `time.monotonic`): route `/trading/assets/positions/list` เริ่มได้ไม่เกิน 1 ครั้งต่อ 4 s หลัง burst 2
  ⇒ **สามครั้งติดกันห่าง ≥ 4 s** และ **≤ 9 ครั้งต่อ 30 s** (อยู่ในทั้ง 10/30s ของเอกสารและ ~2/3.5 s ที่วัดได้ เหลือ margin ≥ 0.42 s)
- เรียกเป็นอย่างแรกใน `BoundedApiClient.get_response` (จุดเดียวที่ทุก request ของ SDK ผ่าน — log มี `sdk_positions` ทุกครั้ง) จึงครอบ retry, ops และ tools; งบและ timeout คำนวณหลังรอ
- งบไม่พอสำหรับการรอ ⇒ `TickDeadlineExceeded` **ก่อนรอและก่อนส่ง** แบบเดียวกับ back-off ของ retry (tick ถัดไปรัน gate ใหม่ทั้งชุด)
- การรอแสดงใน log เป็น `lego_operation` `operation=pace_positions` (INFO) และ flight recorder บันทึกเป็น phase
- ต้นทุน: ครั้งที่สามรอ `max(0, 4 − t)` s — replay 17 tick: รอ 13 tick, มากสุด 1.033 s (18:45), รวม ≈ 5.9 s ทั้ง session; แทน 429 + 2.15 s + request ที่เสียเปล่า
- ไม่เว้นจังหวะ balance / accounts (อ่าน ≤ 1 ครั้งต่อ tick และหลักฐานเป็นราย endpoint)

## ทดสอบ (`test_audit_20261031.py`)

- gateway double = token bucket ราย route (ความจุ 2, เติม 1 ต่อ R s, ครั้งที่ถูกปฏิเสธไม่เสีย token) + นาฬิกาปลอม; ใช้ offset จริง 17 tick (ไม่มี id)
- ไม่มีการเว้นจังหวะ + R = 3.52 s ⇒ **429 ทั้ง 4 tick กลับมาที่ครั้งที่สามตรงกับ log** และ retry ผ่านตาม log
- มีการเว้นจังหวะ ⇒ **0 × 429 ทั้ง 17 tick** ภายใต้แบบที่เข้มกว่า gateway จริง (R = 3.6 s ซึ่งจะปฏิเสธครั้งที่สามที่ log บอกว่าผ่าน 4 tick และ sliding window 2 ต่อ 3.6 s);
  ครั้งที่สามเริ่มที่ `max(t, 4.0)` พอดี
- schedule สุ่ม 5 seed × 30 ครั้ง: สามครั้งติดกันห่าง ≥ 4 s, ≤ 9 ใน 30 s (ครอบการอ่านครั้งที่สี่ด้วย); route อื่นไม่เคยรอ; งบไม่พอ ⇒ หยุดก่อนรอ/ส่ง; มี event `pace_positions`
- ค่าที่ deploy อยู่ (YAML) ผ่าน config, เป็น paper + preview-only และส่งถึง Preview ได้**โดยไม่มี ack เงินจริง**; authorization ของ paper ใช้กับ `LEGO_MODE=trade` ไม่ได้ และ trade ที่ไม่มี ack ถูกบล็อก
- ทั้งชุด **2,303 passed / 9 skipped** (baseline 2,291 + 12, ไม่แก้เทสต์เดิม; 9 = เทสต์ emulator), เวลา 57.8 s (baseline 63.2 s — ไม่มีเทสต์ใดรอจริง);
  mutation 4/4 ถูกจับ (ไม่เรียก `_pace` · interval 3.4 · burst 3 · ตัด budget check)

## ทดสอบ paper ต่อ (ทำโดยเจ้าของ)

1. หลัง merge: clone `main` ใหม่ใน Cloud Shell แล้วรัน **ก่อน 2026-11-05T21:00Z** (ควรนอก 14:30–21:00Z; script บังคับนอก session เฉพาะ trade)

   ```bash
   LEGO_MODE_OVERRIDE=paper LEGO_FIX_C_OVERRIDE=3000 LEGO_DIFF_OVERRIDE=5 bash deploy/cloudshell-prod-observe.sh
   ```

   **ต้องระบุ `LEGO_DIFF_OVERRIDE=5`**: ค่าเริ่มต้นของ script คือ 25 ซึ่งเปลี่ยน `config_hash` ⇒ chain paper ใหม่เริ่มจาก 0 หุ้น;
   DNA (`strategy.uat-continuous.json`), UBER และเศษหุ้นใช้ค่าเริ่มต้นที่ตรงกับที่ deploy อยู่แล้ว; script ถามราคาล่าสุดและการยืนยันเรื่อง Preview เหมือนรอบก่อน
   chain และ holdings ของ paper เดินต่อ (chain key และ `runtime_identity_fingerprint` ไม่ขึ้นกับ candidate) — dashboard PAPER ต้องเห็นแถวต่อจากแถวเดิม ไม่ใช่ p0 ใหม่
2. session ถัดไป: คำสั่งแรกไม่ควรมีสักบรรทัด; คำสั่งที่สองคือเวลาที่รอ ปกติ 1 บรรทัดต่อ order tick (replay วันที่ 30 ต.ค.: ≤ 1,033 ms) —
   ถ้ามี 429 อีก ให้ส่ง request id ไปพร้อม export ชุดใหม่ (`tools.trace_audit` แสดงใน `WEBULL_SDK_ERRORS`)

   ```bash
   gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="lego-tick-prod" AND textPayload:"TOO_MANY_REQUESTS"' --project=lego-firebase --freshness=1d --limit=50 --format='value(timestamp)'
   gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="lego-tick-prod" AND jsonPayload.operation="pace_positions"' --project=lego-firebase --freshness=1d --limit=100 --format='value(timestamp,jsonPayload.duration_ms)'
   ```

3. ระหว่างทดสอบ **อย่าซื้อขาย UBER หรือค้าง order UBER ในบัญชีจริง**: position จริงที่ขยับหรือ open order หลัง Preview ตั้ง operator halt ของ paper (ปลดด้วย `ops.py clear-operator-halt` + ผู้ตรวจคนที่สอง)
