## ค่า notional ที่แนะนำเมื่อ `LEGO_FIX_C=10000`

ขนาด order = |holdings × ราคา − FIX_C| ÷ ราคา ≈ FIX_C × การเคลื่อนไหวของราคาตั้งแต่ rebalance ล่าสุด
cap จึงตั้งเป็น FIX_C × การเคลื่อนไหวสูงสุดที่ยังอยากให้ rebalance เอง × margin และต้อง**ต่ำกว่า FIX_C มาก**
เพื่อบล็อกกรณีอ่าน position เป็น 0 แล้วซื้อทั้ง principal ใบเดียว

| ใช้กับ | notional | % principal | quantity (UBER ≈ 67–68) | orders/session |
|---|---|---|---|---|
| UAT ต่อเนื่อง | **1,500** | 15% | 30 | 26 (= slot ต่อ session) |
| PROD canary | **1,000** (หรือ 500–750 ถ้ายอมบล็อก gap ใหญ่) | 5–10% | 20 | 10 |
| t0 / initial funding (order แรก ≈ FIX_C) | **12,500** | 125% | 200 | 2 — release รอบ funding เท่านั้น |

- หลักฐาน: order ใหญ่สุดใน 19 slot คือ 86.07 USD (0.86%); ราคาทั้งวันเคลื่อน 1.42% → 1,500 ≈ 17× ของ order ใหญ่สุด,
  150 (audit rev2) ≈ 1.7× จะบล็อก gap ตอนเปิดตลาด ~1.5% ที่ยังเป็น rebalance ปกติ, 36,000 = 418×
- **PROD ห้ามเกิน 25% (2,500)** — เป็น BLOCK ของ `release_horizon`; release รอบ funding ได้ถึง 125%
- **t0 ชน cap แน่นอนถ้าใช้ cap ปกติ**: `ExecutionLimits.check` บล็อกเมื่อ `qty > cap` หรือ `qty × ราคาสด ณ dispatch > notional cap` (`>` จึง = cap ผ่าน);
  ราคา dispatch เลื่อนจาก decision ได้ ≤100 bps (`DEFAULT_MAX_DISPATCH_PRICE_DRIFT_BPS`) → order t0 ≈ 10,000 อาจเป็น ~10,100
  cap ต่ำสุดที่ไม่บล็อก t0 = 10,100 (cap = 10,000 เป๊ะ จะบล็อกสุ่มเมื่อราคาขยับขึ้น) และ qty cap ต้อง ≥ FIX_C ÷ ราคา (UBER ≈ 148)
  cap ปกติ 1,500/1,000 + qty 30/20 จะบล็อก order t0 ด้วย `EXECUTION_LIMIT_BLOCKED` ทุก slot และไม่เติม position เอง (fail-safe แต่ไม่เทรด)
- **UAT วันนี้ไม่ใช่ t0**: บัญชีถือ 147.13455 หุ้น (≈ 9.9–10.1k USD) → chain ใหม่ (`bypass:6500` = `config_hash` ใหม่) เริ่มจาก holdings จริง
  order แรกประมาณ 55–86 USD ที่ราคา 67–68 ผ่าน cap 1,500; ถ้า Webull รีเซ็ตบัญชี UAT ให้ใช้ release funding
- วิธีที่ไม่แตะ money path คือ**สอง release**: (1) funding 12,500 / 200 / 2 + ack `initial-funding` → รอ fill ยืนยันและ holdings ตรง
  → (2) release steady 1,500|1,000 / 30|20 / 26|10 หรือ pre-fund ด้วยมือก่อน (แนะนำสำหรับเงินจริง: order ~10,000 ใบเดียวคือความเสี่ยงสูงสุดของระบบ)
  `ops.py release-plan --initial-funding` ตรวจและพิมพ์ชุดพารามิเตอร์ของ release funding

| G6 เงินจริง | NO-GO | PROD observe ≥2 sessions, token NORMAL ที่ rotate โดยคน, เจ้าของบัญชีกำหนด FIX_C/caps/window เอง, canary ตาม runbook |

ข้อจำกัดที่ต้องรู้
- acknowledgement/gate เป็น **review checkpoint ไม่ใช่ security boundary เชิงเข้ารหัส**: release binding เป็น fingerprint ที่คำนวณซ้ำได้
  ผู้ที่ตั้ง env ของ function ได้ย่อมตั้ง ack ได้เอง — ป้องกันความผิดพลาดและ rollout ที่ไม่ได้ตรวจ ไม่ใช่ผู้ที่มีสิทธิ์แก้ deployment
- candidate hash ขึ้นกับว่ามี checkout ของ `lego-firebase-streamlit` อยู่ข้างเคียงหรือไม่ (scope `backend-only` / `backend-and-reader`)
  `candidate-final.json` ของ PR นี้เป็น `backend-only`; ผู้ deploy ต้องคำนวณ (หรือให้ script คำนวณ) จาก checkout จริงของตนเสมอ
- sandbox ที่ใช้ทำงานเข้า `developer.webull.co.th` ไม่ได้ จึงไม่ได้ดึงหน้า contract ซ้ำ ใช้ `webull-llms.txt` ที่แนบ และ `WEBULL_CONTRACT_SOURCES.md` เดิม
- ข้อสังเกตนอกขอบเขตของ PR นี้: node `webull_lego_errors` โตไม่จำกัด (473 รายการในช่วงนี้) ควรมี retention แยกต่างหาก
